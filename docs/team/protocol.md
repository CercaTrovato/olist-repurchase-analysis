## 共同的业务和数据口径

- **主线 A**。CRM／留存运营经理每期只能评审部分已有客户。用过去 6 个自然月的信息，在同一批符合资格的客户中评估前 10% 名单能覆盖多少后续 90 天复购者。主要对照是最近购买优先。容量 10% 是离线假设。
- **补充 B**。历史分群画像可提出一个可测试的内容主题。给出群规模、品类购买人数、分母、窗口和参考比例。真实触达增量、营销收益和成本需要另有实验或记录。
- **样本草案由 1、3、6 号共同核定**。一行代表一位匿名客户在一个分析日的快照。键为 `customer_unique_id` 加 `snapshot_date`，日期格式 `YYYY-MM-DD`。窗口用原始记录的时间口径，香港时间用于交件。历史窗口含起点、排除快照日。仅纳入历史窗口至少有一笔已批准、商品金额大于 0 的订单的客户。未来标签窗口从快照日开始，包含起日，排除结束日 `snapshot_date + 90 days`。存在至少一笔同口径批准订单记 `y=1`，覆盖足够且无此类订单记 0。数据尾部覆盖不足时先排查，保留缺口记录。
- **先记录时间设计**。为训练、验证、最终评价列明快照日期和标签结束日，训练标签需在后续评价时点前成熟。预处理及聚类仅在约定的开发训练数据上拟合，验证和最终评价只做转换及预测。2018-04-01 探索结果已被查看。团队优先查找未用于选模且后续覆盖足够的时间窗口。若没有合适窗口，明确采用冻结后的时间回测，披露结果的探索性质和各窗口重叠或相关性。开发／验证期间只分享相应标签，最终评价标签由 1 号保管至方法冻结。
- **排名规则**。每个评价快照分别计算。取 `K = ceil(0.10 × N)`，模型按分数降序，同分按匿名客户键升序。最近购买按 `R` 升序（距最近批准订单的时间），同分规则一致。给出 `N`、实际正例数、`K`、命中数、精确率（命中／K）、召回率（命中／正例数）与 AP。零分母记 NA，保留计数。记录随机选择的期望命中 `K × 正例数 / N`。跨期先逐期报告，再说明汇总方法。
- **区分两份旧样本**。现有分类脚本使用已批准订单；旧分群脚本用截至快照已送达订单。两者可参考实现。新分群与新分类都由 H02 的资格和快照键出发。旧 `results/` 与正式阶段分开。

### 最小文件结构

| 文件 | 最小列或字段 |
|---|---|
| `snapshot_features.csv` | `customer_unique_id,snapshot_date,split,R,F,M`，再加已核可用的特征。每位客户每个快照只一行。字段字典说明类型、单位、来源和可用时点 |
| `snapshot_labels.csv` | `customer_unique_id,snapshot_date,split,y`。一份文件只含已开放的时间划分。最终评价标签另行保管 |
| `data-manifest.json` | `data_version`、原始包清单或哈希、产物哈希、代码提交或版本、生成命令、时间边界、每快照人数／正例数（未开放的正例数仅保留在 1 号私有记录）、缺失和排除说明 |
| `validation_predictions.csv` | `customer_unique_id,snapshot_date,y,score,selected_top10,selected_recency_top10`，两个标志用 0/1。优先交每个快照的完整验证人群。模型版本和输入数据版本写交接单 |
| `validation_clusters.csv` | `customer_unique_id,snapshot_date,cluster_id`。群号仅在同一聚类版本内解释。群规模、特征输入和映射规则另附 |
| 组内分析表 | 快照、群、客户数、正例数、模型及基线各自的入选数、命中数、漏判数、各指标及分母。不同群在同一全局前 10% 名单中核算 |

CSV 用 UTF-8。保留匿名 ID 为字符串。连接时按组合键作一对一检查，先报告重复、只在左边或只在右边的键和影响人数。内连接后减少的样本要明示原因，双方核定后才继续比较。所有交接同时注明数据版本和产物版本。

## 群里怎么沟通

在已有团队群固定一条交接索引，同一事项用一个 ID 和记录链接跟进。小件在群内共享的记录写清字段，大件用团队私有空间传。公开 GitHub 可放经核对的代码、文档、汇总表及脱敏问题单。逐行客户数据、私有链接、成员资料、成绩和 Canvas 回执留在组内。

**发送者复制下面的格式。**

```text
[H04] 3号 → 5号、6号 | v0.1 | 待验收
输入版本与范围：
交付文件与位置：
行数 / 正例数 / 检查结果：
已知缺口与受影响范围：
请接收方核对什么 / 希望何时回复（香港时间）：
```

**接收者回复一条。** 用「已验收」「退回补件」或「暂收，部分可用」。带上 ID、版本、实际核过的键数／分母，指出尚缺什么、影响哪一步、由谁补和预计何时可补。发送方修订后再交新版本，保留旧版和变更理由。发现上游字段、标签或人群变化时，由 1 号标注下游需要重跑的表。模型和群版本变化由各自负责人告知 5、6 号。

**有阻塞时尽快回报。** 写清「缺哪项输入、谁能提供、影响哪个交件、预计恢复时间、目前可先做什么」。短暂缺件可先交结构、跑法和实际缺口。涉及样本或正式口径的取舍由 6 号协调相关岗确认。涉及最终评估的变动另留记录，禁止拿已看的最终评价结果调参后继续称它为独立测试。

## 交给 Agent 的共通要求

先读自己的岗位任务和本页。核对实际目录、输入版本、文件哈希与日期口径。把本岗的代码、命令、日志、表图和交接单做齐，保留失败和未运行部分。成员本人核查后再发出、提交或合并。原始 CSV、ZIP 和旧探索输出保持只读。
